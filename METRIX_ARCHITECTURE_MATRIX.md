## 11. Sixth operation (same session) — Payment Lifecycle fix (real OVERDUE + genuine partial payment): ACCEPTED

Commit `40e4ad4`, pushed, deployed, production-verified with **organically-created production data** (real account, real "Atlas Insaat" customer) — closes the gap §10 was correctly called out on. Root cause: `Payment.status` could never reach `OVERDUE` (no code path anywhere wrote it) and could never reach `PARTIAL` through any real UI (only a full-remaining-balance "mark as paid" button existed) — so domain #13's AI dunning review (§10) had real infrastructure but no way to ever see real data in production.

**Scope**:
- `reconcileOverdueStatuses` (`payment.repository.ts` + `payment.service.ts`): a deterministic, rule-based status transition — `PENDING`/`PARTIAL` payments past `dueDate` become `OVERDUE`. This is exactly the Tahsilatlar Anayasası's own "Otomatik Alanlar: Durum" contract (an automatically-computed field), not a new mutation authority — no Action Registry entry, no approval, same class of mechanism as the existing CollectionAction sync. Called from `listPayments()` (every Payment read reflects true status) and from `syncAiCollectionActions` (AI suggestions see fresh OVERDUE data).

## 15. METRIX Living Runtime Consistency Operation — items 5 and 6 above closed, single architectural class proven (ACCEPTED, production-verified)

### 15.1 Answer: same architectural class, not the same code defect

Neither shares a line of code — item 6's proximate cause lives in `src/lib/customers/customer-create-semantic-intent.ts` (a Turkish-language intent parser); item 5's lives in `src/components/living-workspace/LivingWorkspaceHost.tsx` / `src/lib/living-workspace/domain-adapters.ts` (a generic list-response reader). ### 15.2 Item 6 (customer-create empty fields) — proven and fixed

**Diagnosis chain** (each step verified with a script/test run, not inferred):
1. Console telemetry (`CustomerConversationExtension`/`CustomerConversation` lifecycle events) on a live repro showed `stage: "customer-create"`, `resultStatus: "NOT_HANDLED"` — the client-side field-aware conversation extension (`customerCreateConversationCoordinator`, which calls a real LLM planner and drives Universal Input field delivery) never ran at all.
2. Traced to its local, synchronous, zero-LLM gate: `extractObviousCustomerCreatePlan` (`customer-create-conversation-planner.ts`), which is called *before* the coordinator and short-circuits to `NOT_CUSTOMER_CREATE` without ever invoking the real planner.
3. Ran `extractObviousCustomerCreatePlan("Yeni müşteri oluştur: Console Debug Test, telefon 5559998877", null)` directly in a vitest scratch test — reproduced `NOT_CUSTOMER_CREATE` deterministically, in isolation, no server involved.
4. Root cause: `resolveCustomerCreateSemanticIntent`'s (`customer-create-semantic-intent.ts`) create-verb regexes ended in a trailing boundary that was wrong twice over — first an explicit `(?=$|\s|[.,!?])` class that didn't include a colon (so "Yeni müşteri oluştur: İsim, ..." — a completely natural way to introduce details — never matched), and a mid-fix attempt at `\b` that made it *worse*: JS's `\b`/`\w` is ASCII-only, so it never matches right after a Turkish letter (ç/ş/ğ/ı/ö/ü) at all — confirmed by a failing 32-test regression suite (`Yeni müşteri aç.`, `Yeni cari aç` etc. all broke). Final fix: a Unicode-aware negative lookahead, `(?!\p{L})` with the `u` flag — verified correct against both the colon case and all Turkish-letter-ending verbs via `customer-create-semantic-intent.test.ts` (32/32 passing, including 3 new colon-phrasing regression cases).
5. Separately confirmed the *delivery* layer downstream (Universal Input field batch, `ExecutiveNavigationCommandHost`) was never broken — production console telemetry showed `hostAvailable:true`, `completionStatus:"COMPLETED"` for the same dispatch mechanism throughout, both before and after this fix. Not a real bug, not fixed, correctly not fixed.)
